# Database migrations

Alembic is the **single source of schema truth**. Do not use
`SQLModel.metadata.create_all` anywhere — that is what caused the same column to
end up with different types on different databases.

## Everyday use

```bash
cd backend

alembic current                      # what revision is this database on?
alembic history --verbose            # the full chain
alembic upgrade head                 # apply everything outstanding
alembic upgrade head --sql           # print the SQL instead of running it
```

`DATABASE_URL` is resolved by `alembic/env.py` from `app.config.settings`, the
same path the app uses. Override it for a scratch database with
`-x db_url=postgresql://...`.

## Adding a schema change

```bash
# 1. Change the SQLModel model under app/models/
# 2. Generate the revision
alembic revision --autogenerate -m "add exploration.archived_at"

# 3. READ THE GENERATED FILE. Always.
# 4. Verify
pytest tests/test_migrations.py -v
alembic upgrade head --sql           # review the actual DDL
```

**Never commit an autogenerated revision unread.** `alembic/env.py` filters out
the `sync_*` schemas and `public.audit_log` so autogenerate cannot propose
dropping them, but that guard only covers objects known at the time it was
written. If you add another table outside SQLModel, add it to `UNMANAGED_TABLES`
in `env.py`.

Things autogenerate does **not** get right in this schema, and which must be
hand-written with `op.execute()`:

- partial indexes (`WHERE ...`) — there are 3
- expression indexes — `idx_sync_source_chunk_fts` uses `to_tsvector(...)`
- GIN indexes — there are 3
- anything in `sync_action` / `sync_survey` / `sync_source`

## Index on a large table

The single transaction in the old startup path made this impossible. It is
possible now:

```python
def upgrade() -> None:
    with op.get_context().autocommit_block():
        op.create_index(
            "ix_thing_created_at", "thing", ["created_at"],
            postgresql_concurrently=True,
        )
```

`sync_action.record` (~50k rows) and `sync_source.content_chunk` (~11k rows) are
the tables where this matters today.

## Revisions

| Revision | Purpose |
|---|---|
| `0001_baseline` | The complete existing schema. **Stamped**, never run, on databases that already have it. Run in full on a new (production) database. |
| `0002_validate_fks` | Validates the 12 foreign keys `startup.py` created `NOT VALID` and never validated. |

## Bringing an existing database under Alembic

Only needed once per database, for databases that already have the schema
(local, staging). **Never run `upgrade head` first** — `0001_baseline` would try
to create tables that already exist.

```bash
# 1. Back up, and test the restore.
pg_dump -Fc "$DATABASE_URL" > pre-stamp.dump

# 2. Prove the baseline matches this database before trusting it.
python scripts/schema_inventory.py snapshot --url "$DATABASE_URL" --rows --out before.json
createdb parity_check
alembic -x db_url="postgresql://.../parity_check" upgrade head
python scripts/schema_inventory.py compare \
    --baseline before.json \
    --candidate-url "postgresql://.../parity_check"
dropdb parity_check
# Must report PASS. Anything under LOSSES or CHANGES must be understood first.

# 3. Record the revision without executing it.
alembic stamp 0001_baseline

# 4. Apply everything after the baseline.
alembic upgrade head

# 5. Prove nothing was lost.
python scripts/schema_inventory.py snapshot --url "$DATABASE_URL" --rows --out after.json
python scripts/schema_inventory.py compare \
    --baseline before.json --candidate after.json --rows-must-not-shrink
```

Step 5 will report the constraint changes `0002` intentionally made. Every other
object must be identical, and no table may lose a row.

**To undo a stamp:** `DELETE FROM alembic_version;` — that is the complete
inverse. `stamp` writes one row and nothing else.

## A brand-new database (production)

```bash
# Pre-flight: must return 0
psql "$DATABASE_URL" -tAc \
  "SELECT count(*) FROM information_schema.tables WHERE table_schema='public'"

alembic upgrade head     # builds all 51 tables
alembic current          # must equal head
```

## Regenerating the baseline

Only before the baseline has been stamped anywhere. Once any database is
stamped, the baseline is frozen — change the schema with a new revision instead.

```bash
python scripts/generate_baseline.py \
    --url "postgresql://user:pw@host:5432/db" \
    --out alembic/versions/0001_baseline.py
```

The generator reads PostgreSQL's own catalog formatters (`format_type`,
`pg_get_expr`, `pg_get_constraintdef`, `pg_indexes.indexdef`) rather than
SQLAlchemy reflection, so types, defaults, partial predicates and `ON DELETE`
actions are reproduced exactly — including drift between models and
`app/migrations/startup.py`.

## Known state

- **`test_no_model_drift` is xfail.** `SQLModel.metadata` and the database
  genuinely disagree: 41 columns are `json` where the raw DDL in `startup.py`
  said `jsonb` (`questionnairequestion.options`,
  `questionnairequestionasset.metadata`, and others), and `report_cache` has
  server defaults in the raw DDL that the model does not declare. The baseline
  reproduces the database as it is, so it is provably correct. Reconciling the
  two belongs in a revision `0003`, after which that test becomes a hard
  assertion.
- **One index reports a rendering difference** in parity checks.
  `idx_sync_source_scrape_url_retry` was created from `status IN (...)`;
  PostgreSQL re-prints the predicate with the casts distributed differently.
  Semantically identical, reported as `RENDERING`, non-fatal.

## The legacy path

`app/migrations/startup.py` still exists and still works, behind
`RUN_STARTUP_MIGRATIONS` (default `false`). It is a cutover fallback only.

Delete it — along with the flag and the call in `app/main.py` — once staging has
run on Alembic alone for two weeks and at least two real schema changes have
shipped through a revision. **Never enable it in production**: production's
schema must come entirely from this revision chain.
